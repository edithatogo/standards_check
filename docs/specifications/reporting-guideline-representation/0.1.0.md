# Reporting-guideline representation and assurance profile 0.1.0

Status: **draft for technical review**. Profile ID:
`dev.standardflow.reporting-guideline-representation`. This is the first immutable
version of the existing draft 0.1 proposal. It has no recorded specification
approval, EQUATOR endorsement or independent scientific acceptance.

## Purpose and conformance

Represent, reconcile and assure reporting standards without transferring authority
from issuing groups to a parser or model. StandardFlow is an optional reference
implementation. Other implementations can satisfy this profile using different
storage formats if they conserve the required identities, distinctions and evidence.
The current implementation uses Canonical Standard Pack v1 and its existing source,
lock and evidence schemas; this profile introduces no replacement pack schema.

Profile version, wire-contract version, guideline edition, pack version, parser
version and model revision are separate identifiers. Never infer one from another.
The terms Must, Should, Could and Won't express this draft's proposed requirements;
a schema-valid file does not establish that all of them have been satisfied.

## Requirements

| ID | Priority | Conformance assertion and evidence |
| --- | --- | --- |
| RGI-01 | Must | Identify issuing authority, family, exact edition/language, stable ID, citation, version and explicit extension/translation/supersession relations; slugs are not identities. |
| RGI-02 | Must | Bind each source artifact to URI, retrieval evidence, byte hash, source type and licence; rights apply to individual text, figures and translations. No presumed licence from catalogue inclusion. |
| RGI-03 | Must | Preserve printed IDs, stable IDs, order, hierarchy, subitems, source wording where permitted and exact source anchors; distinguish missing from not applicable. Independent complete-row comparison and negative mutations. |
| RGI-04 | Must | Separate verbatim text, normalized requirement, explanation, local interpretation and manuscript evidence. A normalized obligation never silently replaces source text. |
| RGI-05 | Must | Preserve modality, actor, action, object, evidence expectation, quantification, conditions, exceptions and coordination; hold unresolved logical scope instead of inventing it. Require anchored interpretation receipts. |
| RGI-06 | Must | Distinguish equivalent, narrower, broader, contradictory and indeterminate mappings using the same explicit applicability universe; inverse mapping, valid witnesses, uncertainty and provenance retained. No similarity or majority-vote admission. |
| RGI-07 | Must | Separate source fidelity, interpretation, rights, applicability, interoperability, usability and external qualification. Missing evidence is a held state, not a negative assessment or passed test. |
| RGI-08 | Must | Deterministic content-addressed packs and derived exports, exact revision/input/version pins, stable keys and schema/order/value conservation. Parquet is a derived view, not authority. |
| RGI-09 | Must | Evaluation receipts bind models, labels, calibration, source pins, disjoint development/held-out families, errors, abstentions and resources; maintain failed receipts and prevent test leakage. |
| RGI-10 | Must | Reporting compliance means evidence that a requirement is addressed, not study-design or methodological quality. Manuscript evidence assessment is a separate contract and benchmark. |
| RGI-11 | Should | Accessible generated checklist/diagram representations, explicit not-applicable/unknown states and tested consumer import/export; fail closed on wrong edition or missing mappings. |
| RGI-12 | Should | Reuse existing provenance, catalogue and packaging vocabularies: PROV-O, DCAT, SKOS with explicit directional semantics, RO-Crate, SPDX and JSON Schema. Map only on a demonstrated consumer need; SHACL if an RDF projection is necessary. |
| RGI-13 | Could | Cross-edition semantic diffs, cross-guideline coverage graph, official translations, extractive manuscript evidence support. |
| RGI-14 | Won't | Claim EQUATOR endorsement, redesign reporting guidance, copy rights-unclear prose, infer universal report quality, construct another canonical schema or service. |


## Relation semantics and uncertainty

For a fixed applicability universe U, let S(A) and S(B) be the nonempty sets of
admissible reporting states satisfying requirements A and B. These are normative
obligations, not similarity of the two sentences or quality scores for a study.

| Relation of A to B | Required evidence within U | Inverse |
| --- | --- | --- |
| Equivalent | S(A) = S(B); both directed implications established | Equivalent |
| Narrower | S(A) is a proper subset of S(B); A imposes the stronger obligation | Broader |
| Broader | S(B) is a proper subset of S(A); B imposes the stronger obligation | Narrower |
| Contradictory | S(A) and S(B) are disjoint despite each being satisfiable in U | Contradictory |
| Indeterminate | Insufficient evidence, incompatible applicability, empty/invalid sets, or overlapping non-nested obligations | Indeterminate |

Example: within a cohort with at least two outcomes, “report every outcome” is
narrower than “report at least one outcome”. It is not equivalent simply because
both mention outcomes. Missing evidence for implication is unknown, not a proved
negative. Contradiction requires evidence that no state in the declared applicability
universe can satisfy both obligations, while each is individually satisfiable.
Exhaustive finite truth sets can establish this; an isolated incompatible
witness cannot. Unsupported cases remain indeterminate. Agent consensus and model probabilities are observations;
they cannot establish these relations by themselves. Store anchors, scope,
applicability, witnesses, abstentions and method identity with each proposed mapping.
Formal control truth sets, natural source-derived pairs and model-agent references
must be reported separately. No transitive equivalence closure over uncertain edges.

## Evidence and admission

Retain separate fields or referenced receipts for source-byte identity, complete
row/anchor fidelity, structure, rights, normalized interpretation, applicability,
migration, downstream conservation and external qualification. A missing receipt
is a hold. Zero applicable requirements, no extracted items and failed acquisition
must not become a passing percentage. Directory coverage counts identities; item
counts retain representation/edition scope and must not be added as unique items.

A pack may be source-reconciled while interpretation or migration remains held.
A successful build, matching row count, public catalogue inclusion, open-access
flag, classifier agreement or conformance-test result does not approve those gates.
Use the existing pack validators and receipt reviewers; the profile registry
validator checks version/approval integrity only.

## Independent triangulation

Compare independent structural readers, deterministic diagnostics, dependency
analysis, bidirectional NLI and an optional typed decision model on the same frozen
inputs. A challenger may be useful by detecting complementary errors even when its
standalone accuracy is lower. Predeclare the decision rule, maximum harmful changes,
coverage, abstention and costs; measure overlap of errors, additional detections,
false equivalence, subgroup behavior, calibration and resource cost. Do not equate
a different architecture with independent errors. Keep adjudicators blinded to
candidate predictions, and never choose the final held-out set after observing
model outputs. Models remain advisory pending separate qualification.

## Versions, decisions and compatibility

`contracts/representation/releases.json` identifies each immutable specification by
semantic version, SHA-256 and exact implementation-schema digests. The first version
is 0.1.0; `approved_version` remains null. A published draft is retained unchanged:
create the next version for amendments. Patch versions clarify without changing an
obligation; minor versions add compatible capability; a breaking change increments
the major version (or minor while pre-1.0), with explicit migration/conservation tests.

Approval is a separate hash-bound decision by the authorized maintainer, referenced
by a durable issue/PR decision, actor and date. Technical approval is not scientific
qualification or external endorsement. The validator can verify receipt structure
and identity; it cannot authenticate a review or approve a standard. Never fabricate
an approval to make a test pass. Repository history preserves previous schema bytes;
only the current profile's implementation pins must match the current schema files.

## Executable reference and limits

- Representation: `schemas/standard-pack.v1.schema.json`; existing Python and Rust
  pack validators, malformed-input fixtures and deterministic pack locks.
- Provenance: `schemas/source-manifest.v1.schema.json`; complete source-row comparison
  and rights-aware source receipts. Content rights remain item-specific.
- Reproducibility: `schemas/standardflow-lock.v1.schema.json`; byte/hash conservation.
- Exchange: `schemas/ecosystem-evidence.v1.schema.json`; producer authority and
  consumer-driven fixtures. Integration claims require receiving-system results.
- Scientific evaluation: the owning Track 01 benchmark and publication protocol;
  no universal conformance score or automatic pack promotion.

Run `python -m scripts.validate_representation_spec`; use `--baseline-revision`
with an exact base commit to enforce immutable prior versions. Actual conformance
must be assessed per requirement and exact implementation revision, with remaining
holds recorded in Conductor. A clean version registry is only governance evidence.

## Existing representations and interoperability

Machine-actionable reporting-guideline schemas and composition already exist.
[Batista et al., Scientific Data (2022)](https://doi.org/10.1038/s41597-022-01707-6)
describe MIRcat/FAIRsharing, JSON-ScheeLD and CEDAR export. Evaluate preservation
and round-trip mappings to these models before proposing another interchange
format or claiming novelty. The proposal here concerns explicit source/edition
fidelity, rights and interpretation boundaries, directional obligation relations
and reproducible assurance. Whether these supply an incremental contribution
requires the prior-art review and empirical evaluation in the publication protocol.

## Interoperability references

Reuse established concepts where a consumer needs them, without asserting an
unimplemented RDF export: [JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12),
